## 已确认仍需服务端配套的遗漏

这些条目不是“已修复”，也不是新的产品方向。本次客户端补丁不能独立宣称完全恢复旧群功能。

1. **等待时换人**：`chat-server/src/plans.ts` 将 reassign 和 remove 一起限制为 proposed；旧行为允许 waiting 时更换 pending/failed 步骤，只有删除步骤限制在开始前。
2. **轮流上下文**：`work.ts::queueRound` 为整圈固定同一个 context_seq，claim 没有在轮到后继发言者时更新；后继伙伴的 `before=context_seq+1` 看不到本圈前面的回复。自动首圈的共同快照应保留，轮流时应推进。
3. **发言顺序与继续讨论**：queueRound 按 actor ID 而非群成员顺序，不轮换第二/三圈起点；continue 开启的新 cycle 仍可能自动并行。需保留原回答者顺序，并让手动继续始终轮流。
4. **@所有人的并行语义**：客户端把所有伙伴写入 mentions，服务器将其视为 named，因而强制轮流。需兼容地表达“全体”与逐个点名，不能通过丢掉 mentions 破坏 mentioned 回复模式。
5. **额度、失败与租约过期**：queueRound 按执行请求数计算 10 条额度而非实际发布回复数；后续圈的推进只在 succeeded 路径，最后结束的是 fail 时可能提前断圈；needs_input 的过期租约也会卡住轮流后继。应保留单成员失败不影响其他伙伴、每圈无发言才提前结束的行为，并提供失败提示。
6. **停止辅助判断后的服务器兜底**：客户端可取消旧模型结果，但 deferExecution 的 planning_deadline 仍可能由 recoverDeferred 自动恢复旧讨论。停止必须同时终止该来源的延迟调度，不能删掉用户消息或关闭全局兜底来规避。

还需按真实执行链核验附件增量投递与跨页历史：现有执行适配器每轮读取最近 100 条，
没有旧实现按专线投递水位读取全部未见附件的机制。一次性恢复 40 上限不等于解决跨页/重复投递。
手动/修改分工失败时的专属轻提示同样需配套，不能把用户明确的分工意图静默改为普通讨论。

## 本次验证与避让

- `chatServerParity.test.ts` 从实际 withChatServer 入口检查请求、辅助判断、取消信号和执行输入，
  使用离线 HTTP/WebSocket fixture；另保留原 chatServer 与辅助模型判断测试。
- Desktop 与 Mobile 均消费同一主机服务；本次不重做 #5613 的卡片、成员 UI、多语言、上传诊断，
  不改 #5587 的工具权限和私聊服务。
- 未跑整仓测试、全包类型检查或多端打包；未启动模拟器、真实 Agent 或向线上群发测试消息。
- 上述服务端清单需独立配套实现与定向回归；需分别记录客户端已合并、服务端已合并、已部署、
  安装包已验收，不能用其中一项代替其余项。
